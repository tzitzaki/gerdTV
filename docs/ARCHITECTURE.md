# Architecture

## Crates
- `crates/gerdtv-core`: all logic, no Flutter dependency, tested headless on Linux.
  - `library.rs`: profiles (non-secret settings in `profiles.json`) and the open profile's library (cache-first open, sync that downloads before locking the database, browse, search, play URLs); `m3u.rs`: the streaming M3U parser; `xtream.rs`: the Xtream Codes client and sync; `db.rs`: the profile database, sync and search (`docs/DATA_MODEL.md`); `playback.rs`: buffer presets and the watchdog.
  - Networking: reqwest with rustls on the ring provider (no C toolchain needed for Android/iOS builds), installed once per process.
  - Performance budgets: `crates/gerdtv-core/benches/budgets.rs` (`just bench`).
- `crates/gerdtv-api` (package `gerdtv_api`): the flutter_rust_bridge surface; types, async functions, event streams, no logic.
- `crates/gerdtv-testkit`: synthetic data, mock servers, fault injection, and the repository rule tests (`tests/repo_rules.rs`).
  - The fault server (`crates/gerdtv-testkit/src/fault.rs`) serves a synthetic clip as endless live TS (timestamps and continuity counters rewritten per loop, so it looks like a real channel to mpv), sliding live HLS (optionally with rotating segment URLs) and seekable VOD, and injects drops, stalls, throttling, HTTP status errors, live end of file and cuts of open streams, from Rust (`set`, `once`, `cut`) or over HTTP (`/_fault/…`). Run it by hand with `cargo run -p gerdtv-testkit --example fault_server`; `just test-integration` starts it for the app's integration tests.
  - The libmpv harness (`crates/gerdtv-testkit/tests/libmpv_watchdog.rs`, `just test-harness`): real libmpv (headless) driven by the real watchdog against the fault server, one test per fault (drop, 5xx, stall, live end of file, throttling, HLS with rotating URLs, 403, timeshift rewind), serially (FFmpeg's log callback is process-wide); `just soak` runs 30 min of random faults (nightly).
  - Generators (`crates/gerdtv-testkit/src/generate.rs`): a seeded synthetic library (30 % live, 50 % movies, 20 % episodes, with prefixes, quality tags, umlauts, years and `S01E02` names) as M3U or Xtream Codes JSON, and an XMLTV guide; 150k entries come to about 45 MB of M3U, 2,000 channels × 7 days to about 300 MB of XMLTV (the 6.4 budgets).
  - Mock servers: an Xtream Codes panel over the generated library (`src/mock_xc.rs`; streams redirect to a fault server), TMDB v3 (`src/mock_tmdb.rs`; umlaut-folded search, details, seasons, 401, 429 with `Retry-After`), and the release download URLs (`src/mock_release.rs`; valid, bad signature, bad hash, downgrade, missing platform, server error, signed with a fixed test key).
  - The clip (`crates/gerdtv-testkit/media`) is generated by `crates/gerdtv-testkit/media/generate.sh` (ffmpeg test sources) and committed, so CI needs no ffmpeg.
- `crates/gerdtv-release`: update key generation, `latest.json` assembly, signing and verification (CI and `just verify-release`).

## The seam (Rust ↔ Flutter)
- `app/flutter_rust_bridge.yaml` points the codegen at `crates/gerdtv-api`; `just codegen` writes the Dart side to `app/lib/src/rust`.
- `app/rust_builder` is a Flutter FFI plugin using Cargokit: every Flutter build (Linux, macOS, Android, iOS) compiles `gerdtv_api` for its targets and bundles `libgerdtv_api`.
- Bridge modules: `api/simple.rs` (start-up), `api/playback.rs` (presets, watchdog), `api/library.rs` (profiles; an opaque `Library` per open profile with sync, categories, items, search pages carrying the caller's sequence number, play URLs). Errors cross as credential-free messages.
- `RustLib.init()` loads the library before the first frame. Widget tests replace it with `RustLib.initMock` and a fake (`app/test/support/fake_core.dart`), so they need no native build.
- Debug: "Failed to load dynamic library" at start means Cargokit didn't build or bundle the library; build with `-v` and look for the Cargokit step.

## Playback pipeline
- One media_kit `Player`. The Rust core owns the policy (`crates/gerdtv-core/src/playback.rs`): `mpv_options` turns a buffer preset into mpv options, and `Watchdog` turns player events into commands. The Dart adapter (`app/lib/player/watchdog_adapter.dart`) sets the options through media_kit's `NativePlayer.setProperty` before `open()`, feeds position/buffering/completed/error events in, ticks it once a second, and runs its commands (reload, show/hide "Reconnecting (n)").
- Watchdog rules (`Watchdog`, table-tested): a live end of file, an error, or no progress for max(15 s, target + 10 s) while not paused by the user (also stuck buffering, or a stream that never starts) schedules a reload with backoff 1, 2, 4, 8, 15, 30 s; while waiting, playing out the remaining buffer doesn't count as recovered; after 3 failed reloads live switches between `.ts` and `.m3u8` (and back), and the form that then plays is remembered per channel; wake from sleep/background and a network change reload live at once; FFmpeg's "HTTP error 401/403" stops with a message (no retry loop); audio-output errors are ignored; VOD reloads resume at the last position and give up after 6 attempts; every recovery episode (trigger, attempts, recovered, seconds) goes to `stream_health`.
- media_kit details the adapter relies on: create players with `WatchdogAdapter.playerConfiguration` (mpv log level warn: FFmpeg reports HTTP status errors as warnings, and media_kit's `error` stream only carries FFmpeg errors starting with `tcp:`); mpv's own "Failed to open <url>" messages contain the URL, so they're classified but never logged.
- Option mapping (names verified in mpv 0.40 and FFmpeg 7.1, and limited to ones mpv 0.36 / FFmpeg 6.0 also have):

| Preset setting | mpv option | Value |
|---|---|---|
| target buffer | `cache-secs`, `demuxer-readahead-secs`, `cache-pause-wait` | the preset's seconds (2 / 8 / 30 / 90 / 1–300) |
| start and resume only with a full buffer | `cache`, `cache-pause`, `cache-pause-initial` | `yes` |
| demuxer size | `demuxer-max-bytes` | target × bitrate × 1.5, at least 32 MiB (bitrate estimate 8 Mbit/s until known) |
| large buffers on disk | `cache-on-disk` | `yes` from 30 s |
| transport reconnect | `stream-lavf-o` | `reconnect=1,reconnect_streamed=1,reconnect_on_network_error=1,reconnect_delay_max=5` |
| network timeout | `network-timeout` | 10 s |

- media_kit's own start-up defaults that stay: `demuxer-lavf-o` (HLS segment retries, allowed extensions), `demuxer-max-back-bytes` (32 MiB until timeshift sets it).
- Timeshift (`timeshift_options`): back buffer `demuxer-max-back-bytes` = window × bitrate (60 min desktop, 30 min phone/tablet/TV), at most a quarter of the free disk, on disk in the app's cache folder (`cache-on-disk` + `demuxer-cache-dir`; embedded libmpv has no default cache folder, so without one it stays in RAM), `force-seekable` and `demuxer-seekable-cache` so rewinding live stays inside the cache. "Behind live" = the live edge (the newest `demuxer-cache-time` before a pause or rewind, plus the time since) minus the position.
- Headless test runs set `ao=null`: with no audio device and no video controller, mpv would end the file at once.

## Native libraries
| Platform | Package | libmpv / FFmpeg | Licence of the build |
|---|---|---|---|
| Linux | `media_kit_libs_linux` | the system libmpv (Debian/Ubuntu package) | as packaged by the distribution |
| Android | `media_kit_libs_android_video` | mpv (2023, between 0.36 and 0.37) / FFmpeg 6.0; arm64-v8a, armeabi-v7a, x86_64; 16 KB page aligned | LGPL-3.0 (FFmpeg), mpv built with `-Dgpl=false` |
| macOS, iOS | `media_kit_libs_macos_video`, `media_kit_libs_ios_video` | mpv 0.36.0 / FFmpeg 6.0 (xcframeworks via CocoaPods) | LGPL |

All are pulled in through `media_kit_libs_video`; LGPL builds combine fine with the GPL-3.0 app. The in-app Licences screen will list them with these flags.

## Desktop windows
`app/lib/platform/mini_window.dart` switches the main window into mini-player mode (480 × 270, hidden title bar, always on top, on all Spaces) and restores its bounds. A second window would be a second Flutter engine that can't share the media_kit player, so the stream would reopen.
